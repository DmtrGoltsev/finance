Status: Wave 2 QA planning artifact for W2-15. This document defines canonical fixture data, scenario coverage, and release evidence layout only. It does not select a test runner, create production code, or override the pending stack ADR.

Scope:

- canonical actors: Owner A, Member B, Other C, Invited, Former;
- fixture graph for accounts, categories, transactions, transfers, invites, sessions, cache/offline state and exports;
- mapping to AS/NEG/SEC/PRIV scenarios, RG gates, TR-RG gates and PF-RG gates;

## Fixture actors

Canonical actor ids are stable labels for all tests and snapshots. Concrete ids may be generated by the future fixture loader, but evidence must retain these labels in metadata.

| Actor | Canonical label | Baseline state | Must see | Must not see | Primary proof purpose |
| --- | --- | --- | --- | --- | --- |
| Owner A | `owner_a` | Active owner/creator in Household AB; owns personal A data | Own personal A data; shared AB data; `shared_family_report` AB; `combined_viewer_overview` A | Member B personal data; Household C data; hidden counts/facets; unsupported transfers | Positive owner and shared-member access; A-side report/export baselines |
| Member B | `member_b` | Active member in Household AB; owns personal B data | Own personal B data; shared AB data; `shared_family_report` AB; `combined_viewer_overview` B | Owner A personal data; Household C data; A personal aggregates/categories/balances | Mirror active-member proof; cross-personal denial |
| Other C | `other_c` | Authenticated user outside Household AB; active in Household C for foreign data | Own personal C data; Household C shared data | Any Household AB data, invites, memberships, reports, exports or shared transfers | Cross-household denial and direct-id neutral errors |
| Invited | `invited_ab` | Pending invite to Household AB; no active membership | Minimal verified invite context only | Shared AB financial data, member list, reports, exports, transfer data before accept | Pre-accept denial, invite-token lifecycle, no token-as-access |
| Former | `former_ab` | Previously active in Household AB; now `left` or `revoked` | Own personal data; optional minimal self membership metadata | Current or historical shared AB financial data through old ids, sessions, caches, exports or cursors | Post-leave/revoke denial and stale artifact invalidation |

Actor setup requirements:

- all actors have authenticated sessions except anonymous security probes;
- each actor has at least one valid current session, one expired/revoked session fixture where relevant, and isolated device/cache context;
- Owner A and Member B are active members of Household AB at baseline;
- Other C is not a member of Household AB and must not be invited to AB;
- Invited has a pending AB invite and no active membership until invite accept scenarios explicitly change state;
- Former has old AB ids, old report cursors, an old export job, and offline/cache snapshots created before `left`/`revoked`.

Graph invariants:

- AB and C data must share overlapping dates, amounts, descriptions and category names to prove access filtering does not rely on harmless-looking data.
- Personal A and Personal B must include same-currency and same-date records so report totals fail loudly if cross-personal rows leak.
- Shared AB and Shared C must include same-currency shared records so cross-household leakage is detectable.
- Fixture labels must not encode secrets, real emails, bank details or production-like tokens.
- Evidence metadata can include fixture labels and synthetic ids, but logs/audit evidence must not contain raw amounts, descriptions, account names, category names, tokens or raw request/response bodies.

## Golden snapshots

Golden snapshots are stable public-response and client-state artifacts. They must be free of runner-specific naming assumptions and must normalize dynamic fields such as `requestId`, generated ids, timestamps and cursors.

Required neutral-error golden groups:

| Group | Compare | Required invariant |
| --- | --- | --- |
| `golden_account_missing_vs_inaccessible` | missing account id vs A personal account requested by B/C/Invited/Former | Same user-facing envelope and no account existence details |
| `golden_transaction_missing_vs_inaccessible` | missing transaction id vs hidden personal/shared transaction id | Same public shape; no amount/description/account/category |
| `golden_category_missing_vs_inaccessible` | missing category id vs hidden personal/foreign category id | Same public shape; no category name/owner/usage |
| `golden_report_filter_hidden` | missing vs inaccessible `householdId`, `accountIds`, `categoryIds`, stale cursor | Neutral response or empty visible behavior per contract; no hidden counts |
| `golden_transfer_hidden_side` | personal->shared, shared->personal, cross-user personal, cross-household shared, missing counterparty | Same safe public message/details for unsupported hidden side |
| `golden_invite_reset_auth_neutral` | missing/used/expired/revoked invite or reset contexts where neutrality is required | No account, email, token or household leakage |
| `golden_export_delete_leave_neutral` | missing vs inaccessible export, deletion request, household and membership ids | No hidden object existence, owner or history hints |

No-hidden-count snapshots:

- list envelopes for accounts, transactions, categories and exports include only returned `items` and post-filter pagination fields;
- report DTOs contain no `hiddenCount`, `filteredOutCount`, `preFilterCount`, global `totalCount`, hidden facets, hidden owner buckets, hidden min/max, household-wide personal totals or member contribution fields;
- autocomplete DTOs contain visible ids/labels only and no counts, hidden-match hints or usage counts based on hidden rows;
- client snapshots contain no copy that implies hidden data exists.

Snapshot hygiene:

- redact or normalize amounts in log/audit evidence; public API response snapshots may include synthetic visible amounts only where needed for report math, but log evidence must prove those values are absent;
- never snapshot real secrets, tokens, passwords, production config, raw request bodies or export file contents;
- include actor label, scenario id, endpoint/surface, fixture labels, expected gate ids and runner-neutral status in snapshot metadata.

## Risks and escalation triggers

P0/P1 gaps in this planning artifact:

- P1 gap: W2-00 stack ADR is pending, so exact test runner, CI report format, DB reset strategy, fixture loader and evidence paths outside this runner-neutral layout are not selected.
- P1 gap: exact rate-limit values and export file TTL remain product/security decisions; fixtures reserve evidence buckets but cannot define final thresholds.
- P1 gap: CSRF/CORS, token/cookie storage, secret manager, backup mechanism, dependency scanner and route inventory tooling depend on the stack ADR.
- P1 gap: no automated test output exists yet; this document only defines required fixture coverage and evidence shape.

Escalate immediately if any future implementation or test result shows:

- personal data of one user appears in another user's list, detail, search, autocomplete, report, export, cache, debug output or client snapshot;
- report aggregation, balance, count, category breakdown, trend, drill-down, export or cache materialization runs before visible account filtering;
- personal/shared, cross-user personal or cross-household shared transfer is allowed, partially written or leaks hidden side details;
- Invited or Former can access shared AB financial data through old ids, sessions, cursors, exports, offline snapshots or caches;
- neutral-error snapshots differ for missing vs inaccessible resources in a way that reveals existence, owner, household, account/category names, amounts, descriptions, tokens or membership state;
- logs/audit/telemetry/crash reports contain amounts, balances, descriptions, account/category names, raw financial payloads, emails in plaintext where avoidable, tokens, secrets or stack/SQL details;
- out-of-scope imports, bank API, broker API, SMS/push credentials, raw bank statements or non-manual `sourceType` acceptance appears;
- public launch, SaaS/self-hosted commitment, formal deletion/retention SLA, former shared-history access, support/admin financial access, 2FA/passkeys or production secret-manager decision enters MVP scope without Product/Security/Privacy/Legal/Ops signoff.
