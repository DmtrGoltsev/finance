# Privacy baseline MVP

## Статус и границы

Этот baseline задает минимальную privacy/compliance рамку для закрытого MVP приложения учета личных и семейных финансов. Документ не выбирает юрисдикцию, не является публичной политикой конфиденциальности и не заменяет юридическую проверку.

MVP строится на практичных допущениях:

- банковские API, SMS/push-import pipeline, перехват SMS/push/notifications и импорт файлов не входят в MVP; capture drafts допускаются только как user-initiated OCR из выбранного пользователем скриншота с подтверждением перед созданием операции;
- счета, операции, категории и описания вводятся пользователем вручную;
- финансовые данные считаются конфиденциальными даже без банковских интеграций;
- personal account видит только владелец;
- shared account видят только активные участники семейного пространства;
- семейное пространство MVP рассчитано максимум на двух участников без сложной ролевой модели;
- публичный запуск, SaaS-модель, выбор юрисдикции, формальная privacy policy, DPA/processor модель и обязательные сроки хранения требуют отдельной юридической проработки до релиза за пределы закрытого MVP.

## Цели privacy baseline

- Понять, какие данные обрабатываются в MVP и зачем.
- Минимизировать состав данных до ручного учета финансов без внешних источников.
- Зафиксировать границы видимости personal/shared данных внутри семьи.
- Дать практичный baseline для уведомления, экспорта, удаления, выхода из семьи, восстановления доступа, retention, логов, телеметрии и backup.
- Явно выделить решения, которые нельзя принимать как инженерные допущения без Product/Legal/Security escalation.

## Data inventory MVP

| Категория данных | Примеры | Источник | Кто видит в продукте | Цель обработки в MVP |
| --- | --- | --- | --- | --- |
| Учетная запись | `user_id`, email/логин, отображаемое имя, статус аккаунта, даты создания/обновления | Пользователь, система | Полный профиль видит сам пользователь; участнику семьи виден только минимальный профиль, нужный для совместного учета | Регистрация, вход, идентификация владельца данных, семейные приглашения |
| Auth/security данные | Хеш пароля, reset-токены в хешированном/одноразовом виде, session/refresh tokens, rate-limit metadata | Система | Не отображаются пользователям; доступны только backend/security процессам | Безопасный вход, выход, восстановление доступа, защита от перебора |
| Семейное пространство | `householdId`, название пространства, `createdByUserId`, статус | Пользователь, система | Активные участники семейного пространства | Общий бюджет и shared-счета |
| Membership и приглашения | Участники, статусы `invited`/`active`/`left`/`revoked`, кто пригласил, даты приглашения/вступления/выхода | Пользователь, система | Активные участники видят состав на минимальном уровне | Управление участием и доступом к shared-данным |
| Счета | Название, тип счета: cash/bank/deposit/brokerage, ownership: personal/shared, валюта, начальный/текущий баланс, статус | Пользователь | Personal видит только владелец; shared видят активные участники семьи | Ручной учет денег и активов |
| Операции | Тип: income/expense/transfer/brokerage, счет, сумма, валюта, дата, категория, описание, автор/редактор, soft delete metadata | Пользователь | Наследуют видимость счета; personal-операции не раскрываются другому участнику семьи | Ручной учет финансовых событий |
| Capture drafts | Структурированные поля предполагаемой операции, `idempotencyKey`/`evidenceHash`, confidence/metadata, статус `pending`/`confirmed`/`discarded` | User-initiated OCR из выбранного пользователем скриншота | Видит пользователь-владелец draft; после подтверждения операция наследует обычную область доступа выбранного счета | Предложить черновик без автосоздания операции и без перехвата или хранения raw SMS/push/notification body |
| Категории и иконки | Название категории, тип, scope personal/household, выбранная иконка | Пользователь, системный каталог | Personal категории видит владелец; household категории видят активные участники | Группировка операций и базовая аналитика |
| Отчеты и аналитика | Период, агрегаты доходов/расходов, остатки, разбивка по категориям, набор видимых счетов | Система на основе видимых данных | Текущий пользователь; shared-отчеты не включают personal-счета другого участника | Базовые отчеты за период |
| Audit events | Время, actor, действие, target type/id, scope, результат, request id, IP/user-agent при наличии | Система | Не являются пользовательским интерфейсом; доступны ограниченным эксплуатационным ролям | Расследование доступа, изменений, удаления, восстановления |
| Application logs и telemetry | Технические события, ошибки, производительность, обезличенные счетчики использования | Система | Команда разработки/эксплуатации с ограниченным доступом | Надежность, диагностика, качество MVP |
| Backup | Резервные копии БД и audit logs | Система | Только ограниченные эксплуатационные роли | Восстановление после сбоя или ошибки миграции |
| Локальный кэш Android/PWA | Минимальные данные сессии и, при необходимости, короткоживущий кэш интерфейса | Клиентское приложение | Пользователь устройства | Работа клиента и UX; не является постоянным хранилищем финансовых данных |

В MVP не обрабатываются и не хранятся: банковские пароли, банковские токены, SMS-коды, push-секреты, API-ключи банков/брокеров, импортированные банковские файлы, исходные выписки, налоговые расчеты, инвестиционные рекомендации и массовые внешние идентификаторы источников. Приложение не перехватывает SMS, push-уведомления или системные notifications; raw body SMS/push/notification не отправляется на backend и не хранится server-side.

## Sensitivity classification

| Уровень | Данные | Baseline-правило |
| --- | --- | --- |
| Public/low | Системные иконки, общие UI-настройки без пользовательского содержания | Можно хранить и логировать без финансового контекста, если они не связаны с пользователем |
| Personal | Email/логин, отображаемое имя, user id, membership metadata | Минимизировать, показывать только при необходимости, не использовать email как security boundary |
| Confidential financial | Названия счетов, типы счетов, балансы, суммы, даты операций, категории, описания, отчеты, связи счетов и операций | Не раскрывать вне области доступа; не писать в plaintext logs/telemetry; защищать в БД, backup и API |
| Confidential family | Состав семейного пространства, приглашения, статусы участия, shared-счета и shared-операции | Показывать только активным участникам; после выхода/отзыва немедленно прекращать дальнейший доступ |
| Highly sensitive free text | Описания операций, пользовательские названия счетов/категорий, кастомные метки, которые могут раскрывать здоровье, долги, работу, отношения или инвестиционное поведение | Считать такими же чувствительными, как финансовые суммы; не использовать в логах, telemetry, debug dumps и публичной поддержке |
| Secrets | Пароли, reset/invite/session/refresh tokens, production secrets | Не хранить в plaintext; не логировать; хранить только хеши или защищенные токены по security baseline |
| Operational confidential | Audit logs, production dumps, backups, incident notes | Ограничить доступ, шифровать where applicable, не переносить в локальную разработку или публичные каналы |

## Минимизация данных

- Для регистрации MVP достаточно email/логина, пароля и минимального отображаемого имени. Юридическое имя, паспортные данные, адрес, телефон, дата рождения и платежные реквизиты не запрашиваются.
- Название семейного пространства необязательно должно содержать фамилию или реальные отношения; UI должен допускать нейтральное имя.
- Счета создаются как учетные сущности, а не как реальные банковские реквизиты: не запрашивать номер карты, номер счета, IBAN, договор, БИК, фото документов или выписки.
- Операции создаются вручную или через подтвержденный пользователем capture draft из локального/on-device OCR выбранного скриншота. Итоговая transaction остается manual-equivalent: до `confirmed` draft не меняет счета и отчеты, после подтверждения проходит те же access/audit/log-redaction правила, что и ручной ввод.
- Приложение не использует SMS receiver, push capture или Android notification listener для создания draft.
- Backend хранит только structured capture draft, `idempotencyKey`/`evidenceHash` и lifecycle status `pending`/`confirmed`/`discarded`; raw SMS/push/notification body запрещен для server-side хранения, логов, telemetry и backup.
- Брокерские операции в MVP фиксируют факт движения денег/актива без налоговой аналитики, инвестиционных рекомендаций и хранения учетных данных брокера.
- Пользовательские free-text поля должны иметь разумные ограничения длины и подсказки не вводить секреты, пароли, номера карт и документы.
- Debug endpoints, export/debug dumps и support-инструменты не должны возвращать данные за пределами видимости текущего пользователя.
- Если аналитика продукта нужна для закрытого MVP, использовать агрегированные счетчики без сумм, названий счетов, описаний операций, email, токенов и идентификаторов семей.

## Consent и notice для семейного пространства

Создание или принятие семейного пространства должно сопровождаться коротким notice до активации shared-доступа:

- shared accounts, shared operations, shared categories и shared reports будут видны всем активным участникам семейного пространства;
- personal accounts, personal operations, personal categories и personal reports не раскрываются другому участнику семьи;
- семейная аналитика пользователя включает shared-счета семьи и personal-счета самого пользователя, но не personal-счета другого участника даже в агрегированном виде;
- участник может выйти из семьи или быть отозван, после чего будущий доступ к shared-данным прекращается;
- данные shared-счетов, уже увиденные другим активным участником до выхода/отзыва, нельзя технически "забрать обратно";
- размещение операции на shared account делает ее видимой семье, включая описание и категорию;
- перевод между personal и shared является privacy-risk и в MVP допускается только при split visibility или запрещается до отдельного решения.

Согласие на участие в семейном пространстве не может даваться одним пользователем за другого. Второй участник должен принять приглашение сам. До принятия приглашения ему не должны раскрываться финансовые данные семьи.

## Права пользователя и практичные MVP-допущения

### Export

- Пользователь может запросить экспорт своих personal data и всех финансовых данных, которые он видит в продукте.
- Экспорт включает personal-счета/операции/категории пользователя, его профиль, membership history и shared-счета/операции/категории, доступные ему как активному участнику.
- Экспорт не включает personal-счета, personal-операции, personal-категории и personal-аналитику другого участника семьи.
- Формат MVP может быть простым: JSON или CSV/ZIP с понятной структурой. Для закрытого MVP допустим ручной/backoffice процесс при условии audit event и проверки области доступа.
- Перед публичным запуском нужен формальный self-service или documented process с юридически корректными сроками ответа.

### Delete account / delete data

- Для закрытого MVP базовый вариант: пользователь может запросить удаление аккаунта; система сначала деактивирует аккаунт, отзывает сессии и прекращает доступ.
- Personal-счета, personal-операции и personal-категории удаляемого пользователя должны быть удалены или необратимо обезличены после короткого operational grace period, если нет отдельного юридического основания хранения.
- Shared-операции, созданные пользователем в семейном пространстве, могут сохраняться как часть общей финансовой истории семьи, но автор должен быть обезличен или заменен на нейтральный deleted user marker, если это не ломает audit/целостность.
- Soft delete допустим для защиты от ошибки пользователя и восстановления после инцидента; физическое удаление должно учитывать backup/retention и выполняться контролируемым maintenance-процессом.
- Обязательное юридическое решение о праве на удаление, сроках выполнения, исключениях, audit retention и backup deletion является escalation trigger.

### Leave family

- Участник может выйти из семейного пространства или быть отозван.
- После выхода/отзыва его active membership прекращается, сессии/кэши должны быть инвалидированы или перестать давать доступ к shared data, а новые запросы к shared accounts/reports должны отклоняться.
- Personal data вышедшего участника не раскрывается оставшемуся участнику.
- Нужно продуктово и юридически подтвердить, сохраняет ли бывший участник доступ к историческим shared-операциям за период участия. До решения безопасное MVP-допущение: после выхода дальнейший доступ к shared-пространству прекращается, а экспорт перед выходом доступен только для данных, которые пользователь видит на момент активного участия.

### Account recovery

- Восстановление доступа должно раскрывать минимум данных и использовать нейтральные ответы, не подтверждающие наличие email/аккаунта постороннему.
- Reset-токены одноразовые, короткоживущие и не хранятся в plaintext.
- После успешного восстановления старые сессии и refresh tokens должны быть отозваны.
- Support-assisted recovery для закрытого MVP допустим только через ограниченный процесс с audit event и без просмотра финансовых значений оператором, если это возможно.
- Любая схема восстановления, требующая проверки личности, документов, телефона или доступа оператора к финансовым данным, требует escalation до реализации.

## Retention baseline для закрытого MVP

Этот baseline задает инженерные допущения, а не юридически утвержденную retention policy.

| Данные | Базовое удержание для закрытого MVP | Удаление/архивация |
| --- | --- | --- |
| Активная учетная запись | Пока аккаунт активен | Деактивация по запросу; удаление/обезличивание после grace period |
| Personal financial data | Пока аккаунт активен и пользователь не запросил удаление | Soft delete для пользовательского удаления; физическое удаление или обезличивание через maintenance-процесс |
| Shared financial data | Пока family space активно или пока участники используют общую историю | Архивирование вместо немедленного удаления, если данные нужны для целостности shared-отчетов |
| Membership и приглашения | Пока нужно для управления доступом и audit | Истекшие/отозванные invite tokens не переиспользуются; секретная часть удаляется/хешируется |
| Сессии и reset tokens | Минимально необходимый срок жизни | Отзыв при logout, смене пароля, выходе из семьи, удалении аккаунта; истекшие токены очищаются |
| Audit logs | Минимально необходимый срок для безопасности закрытого MVP | Конкретный срок является юридическим/product/security решением перед публичным запуском |
| Application logs | Короткое operational окно для диагностики | Автоматическая ротация; без финансовых значений и секретов |
| Telemetry | Только агрегированные/минимальные события | Удаление raw-событий по короткому окну; без user-content |
| Backups | Минимум для восстановления закрытого MVP, согласованно с security baseline: daily backup, RPO/RTO до 24 часов | Старые backups ротируются; удаление пользовательских данных из backup может выполняться через истечение backup retention, если нет юридического требования быстрее |

Перед публичным запуском или SaaS-моделью нужно утвердить формальные сроки retention, deletion SLA, backup deletion approach и исключения для audit/security.

## Logging и telemetry privacy rules

- Логи и telemetry не являются местом хранения финансовых данных.
- Запрещено писать в plaintext: суммы, остатки, названия счетов, описания операций, пользовательские категории, email, пароли, session/refresh tokens, reset tokens, invite tokens и production secrets.
- Request/response body logging в production/staging с реальными данными запрещен по умолчанию.
- Ошибки API не должны подтверждать существование чужого account/operation/family id.
- Audit events должны фиксировать факт действия и область доступа без финансовых значений: actor, action, target type/id, scope, result, timestamp, request id.
- Crash reports и frontend telemetry должны проходить фильтрацию пользовательского ввода и не содержать экранные снимки с финансовыми данными.
- Для продуктовой аналитики MVP использовать coarse events: регистрация, создание счета, создание операции, открытие отчета, принятие приглашения. Не включать суммы, описания, названия счетов/категорий и состав семьи сверх минимального event context.
- Доступ к логам, telemetry и audit ограничивается по least privilege и сам по себе должен быть аудируемым для production-like окружений.

## Backup/privacy notes

- Backups содержат конфиденциальные финансовые и семейные данные, поэтому должны иметь не меньшую защиту, чем production database.
- Backup должен быть encrypted at rest и передаваться только по защищенным каналам.
- Backup-хранилище изолируется от runtime-учетной записи приложения; приложение не должно иметь права удалять backups.
- Restore проверяется на отдельном окружении минимум один раз до релиза MVP.
- Выборочное восстановление не должно раскрывать данные другой семьи или пользователя и должно сохранять tenant boundaries.
- Production backups и database dumps нельзя переносить в локальную разработку, публичные buckets, issue trackers, chat attachments или незащищенные файловые обменники.
- Доступ к backup/restore фиксируется audit event.
- Backup retention и способ удаления пользовательских данных из backup после delete request требуют юридического решения перед публичным запуском/SaaS.

## Post-MVP юридические вопросы

- Выбор юрисдикции и применимых privacy laws для публичного запуска.
- SaaS, self-hosted или hybrid модель: роли controller/processor, DPA, subprocessors, hosting region, data residency.
- Формальная privacy policy, terms of service, consent/notice language и процесс обновления документов.
- Возрастные ограничения и запрет/разрешение использования несовершеннолетними.
- Правила account deletion, data deletion, export SLA, retention periods и backup deletion.
- Правовая модель shared family data: кто может удалять/экспортировать shared history, что происходит при конфликте участников или выходе из семьи.
- Support/admin access policy: когда оператор может видеть production data, как фиксируется доступ, нужна ли break-glass процедура.
- DPIA/PIA или аналогичная оценка рисков для финансовых и семейных данных перед публичным запуском.
- Условия подключения банковских API, брокерских API, SMS/push и импорта файлов.
- Требования к breach notification, incident response и пользовательским уведомлениям.
- Политика cookies, мобильной/PWA telemetry и third-party analytics.
- Использование облачных провайдеров, crash reporting, email delivery и других subprocessors.

## Escalation triggers

Эскалировать к Product, Legal, Security Architect и Operations до реализации или релиза, если появляется любое из условий:

- нужно принять обязательное юридическое решение по юрисдикции, публичному запуску, SaaS/self-hosted модели или обработке персональных данных;
- нужно утвердить публичную privacy policy, terms, consent wording, DPA или список subprocessors;
- нужно выбрать обязательные сроки retention, deletion SLA, account deletion flow или правила удаления из backup;
- нужно определить, кто владеет shared family data и кто может удалить/экспортировать shared history;
- требуется показывать personal account, personal transaction, personal category или personal aggregate другому участнику семьи;
- требуется разрешить transfer personal -> shared без split visibility или без отдельного product/security решения;
- добавляются банковские API, брокерские API, SMS/push, импорт файлов, внешние финансовые идентификаторы или хранение банковских/API секретов;
- появляется support/admin процесс, в котором человек может видеть финансовые значения пользователей;
- telemetry/crash reporting начинает собирать user content, screen recording, screenshots или granular financial events;
- закрытый MVP превращается в публичный beta/production или начинает обрабатывать данные пользователей вне доверенного пилота;
- расширяется семейная модель: больше двух участников, детальные роли, дети/несовершеннолетние, delegated access;
- обнаружена утечка финансовых данных, ошибочное раскрытие personal/shared, повторная проблема с логами/backup или failure restore;
- нужно принять решение о хранении данных в конкретной стране/регионе или переносе данных между регионами;
- требуется юридически значимый процесс восстановления доступа с документами, телефоном или ручной проверкой личности.

## Definition of done для privacy MVP

- Есть data inventory и sensitivity classification для MVP.
- Подтверждено, что personal account, personal operations, personal categories и personal reports видит только владелец.
- Подтверждено, что shared account, shared operations, shared categories и shared reports видят только активные участники семейного пространства.
- MVP не собирает банковские секреты, SMS/push секреты, API credentials и файлы импорта.
- Есть практичный baseline для export, delete account/data, leave family и account recovery.
- Есть retention baseline для закрытого MVP без выбора юрисдикции.
- Логи, telemetry, crash reports и audit не содержат финансовые значения, пользовательский free text и секреты.
- Backup/privacy правила согласованы с security baseline.
- Публичный запуск, SaaS/self-hosted, юрисдикция, formal retention/deletion и юридические документы явно вынесены в post-MVP/escalation.
