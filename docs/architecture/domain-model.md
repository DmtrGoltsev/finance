# Доменная модель MVP

## Контекст и границы MVP

MVP фиксирует доменную модель приложения для ручного учета личных и семейных финансов. Пользователь может зарегистрироваться, создать финансовое пространство, вести личные и общие счета, вручную добавлять операции, настраивать категории с иконками и смотреть базовую аналитику за период.

Граница MVP:

- учетные записи пользователей и вход в продукт;
- семейное пространство максимум для двух участников;
- личные и общие счета;
- ручное создание и редактирование счетов, операций, категорий и иконок;
- операции дохода, расхода, перевода и базовые брокерские операции без налоговой аналитики;
- базовые отчеты по доходам, расходам, категориям и остаткам за период;
- Android и PWA/браузерный клиент как каналы доступа без привязки доменной модели к конкретному стеку.

MVP не зависит от импорта, банковских API, SMS/push-интеграций, дедупликации импортов и внешних источников данных. При этом модель оставляет место для будущего добавления источника операции и внешних идентификаторов без изменения базовых связей `User -> Account -> Operation`.

## Основные принципы модели

- Личный счет видит только владелец.
- Общий счет видят активные участники семейного пространства.
- `shared family report` строится только по общим счетам, операциям и категориям household.
- `combined viewer overview` строится по общим счетам household и личным счетам текущего пользователя.
- Личные счета другого участника не раскрываются ни в списках счетов, ни в операциях, ни в агрегированной аналитике.
- Видимость операции наследуется от счета, к которому она относится.
- Настройки категорий и иконок могут быть личными или семейными; семейные настройки доступны участникам семейного пространства.
- Все финансовые изменения в MVP создаются и редактируются вручную пользователем.

## Сущности

### User

Назначение: представляет учетную запись человека, который ведет личные финансы и может участвовать в семейном пространстве.

Владелец: сам пользователь.

Область видимости: профиль видим самому пользователю; другим участникам семейного пространства видимы только минимальные данные, необходимые для совместного учета, например отображаемое имя.

Ключевые поля:

- `id`;
- `displayName`;
- `email` или иной идентификатор входа;
- `authStatus`;
- `createdAt`;
- `updatedAt`;
- `deactivatedAt`, если учетная запись отключена.

Lifecycle:

1. Пользователь регистрируется.
2. Пользователь входит в продукт и получает личное финансовое пространство.
3. Пользователь может создать семейное пространство или принять приглашение.
4. Пользователь может менять отображаемые данные.
5. Пользователь может быть деактивирован; его исторические операции сохраняют ссылку на автора для аудита.

### Family / Household

Назначение: объединяет до двух пользователей в семейное пространство для общего бюджета и общих счетов.

Владелец: пользователь-создатель семейного пространства; в MVP детальные роли не вводятся.

Область видимости: доступно активным участникам через `Membership`.

Ключевые поля:

- `id`;
- `name`;
- `createdByUserId`;
- `createdAt`;
- `updatedAt`;
- `status`: active, archived.

Lifecycle:

1. Пользователь создает семейное пространство.
2. Создатель приглашает второго пользователя.
3. Второй пользователь принимает приглашение и становится активным участником.
4. Семейное пространство используется для общих счетов, семейных категорий и семейной аналитики.
5. Семейное пространство может быть архивировано; исторические данные сохраняются.

### Membership

Назначение: связывает пользователя с семейным пространством и определяет его участие.

Владелец: семейное пространство.

Область видимости: активные участники видят состав семейного пространства на уровне, достаточном для совместного учета.

Ключевые поля:

- `id`;
- `householdId`;
- `userId`;
- `status`: invited, active, left, revoked;
- `invitedByUserId`;
- `invitedAt`;
- `joinedAt`;
- `endedAt`.

Lifecycle:

1. Создается приглашение для пользователя.
2. Приглашение принимается, и membership становится active.
3. Участник может выйти или быть отозван из семейного пространства.
4. После выхода пользователь теряет доступ к общим счетам и операциям, но исторические операции сохраняют ссылки на автора и редактора.

### Account

Назначение: отражает место учета денег или активов: наличные, банковский счет, вклад, брокерский счет.

Владелец: для личного счета владелец - конкретный `User`; для общего счета владелец - `Household`.

Область видимости:

- `personal`: виден только `ownerUserId`;
- `shared`: виден активным участникам `householdId`.

Ключевые поля:

- `id`;
- `name`;
- `accountType`: cash, bank, deposit, brokerage;
- `ownershipType`: personal, shared;
- `ownerUserId`, обязателен для personal;
- `householdId`, обязателен для shared;
- `currency`;
- `initialBalance`;
- `currentBalance`, если баланс хранится как доменное состояние, либо вычисляется из операций;
- `status`: active, archived;
- `createdByUserId`;
- `createdAt`;
- `updatedAt`;
- `archivedAt`.

Lifecycle:

1. Пользователь вручную создает счет.
2. Счет получает тип, название, валюту и ownership.
3. Счет используется в операциях.
4. Пользователь с доступом может редактировать название и параметры, не нарушающие историю операций.
5. Счет архивируется вместо удаления, если на нем есть операции.

### Operation / Transaction

Назначение: фиксирует финансовое событие вручную: доход, расход, перевод или базовую брокерскую операцию.

Владелец: счет, на котором создана операция; операцию создает конкретный пользователь.

Область видимости: наследуется от `accountId`. Для перевода с участием двух счетов операция видима пользователю только если он имеет доступ к соответствующей стороне перевода. В MVP предпочтительно разрешать перевод только между счетами, видимыми текущему пользователю.

Ключевые поля:

- `id`;
- `operationType`: income, expense, transfer, brokerage;
- `accountId`;
- `counterpartyAccountId`, опционально для переводов;
- `categoryId`, обязательно для income/expense, опционально или специализировано для transfer/brokerage;
- `amount`;
- `currency`;
- `occurredAt`;
- `description`;
- `createdByUserId`;
- `lastEditedByUserId`;
- `createdAt`;
- `updatedAt`;
- `deletedAt`, если используется мягкое удаление;
- `sourceType`: manual в MVP, с возможностью future import/api;
- `externalReference`, опционально для post-MVP, не используется в MVP.

Lifecycle:

1. Пользователь вручную создает операцию на доступном ему счете.
2. Пользователь заполняет дату, сумму, счет, категорию и описание.
3. Пользователь с доступом к счету может редактировать операцию; фиксируется последний редактор.
4. Операция участвует в расчетах остатков и аналитике.
5. Операция может быть исправлена или мягко удалена; удаленная операция не участвует в текущей аналитике, но может сохраняться для истории.

### Category

Назначение: классифицирует доходы и расходы для ручного ввода и аналитики.

Владелец: `User` для личной категории или `Household` для семейной категории.

Область видимости:

- личная категория видна только владельцу;
- семейная категория видна активным участникам семейного пространства.

Ключевые поля:

- `id`;
- `name`;
- `categoryType`: income, expense;
- `scope`: personal, household;
- `ownerUserId`, обязателен для personal;
- `householdId`, обязателен для household;
- `iconId`;
- `status`: active, archived;
- `createdByUserId`;
- `createdAt`;
- `updatedAt`;
- `archivedAt`.

Lifecycle:

1. Пользователь создает категорию вручную.
2. Пользователь выбирает или настраивает иконку.
3. Категория используется в операциях.
4. Категория может быть переименована или получить другую иконку.
5. Категория архивируется вместо удаления, если уже использовалась в операциях.

### Icon

Назначение: визуально маркирует категории и, при необходимости, счета.

Владелец: системный каталог, пользователь или семейное пространство в зависимости от происхождения иконки.

Область видимости:

- системные иконки доступны всем пользователям;
- личные иконки доступны владельцу;
- семейные иконки доступны участникам семейного пространства.

Ключевые поля:

- `id`;
- `name`;
- `source`: system, custom;
- `scope`: global, personal, household;
- `ownerUserId`, если scope personal;
- `householdId`, если scope household;
- `visualRef`: ссылка на имя, токен или ресурс иконки без привязки к способу хранения;
- `createdByUserId`;
- `createdAt`;
- `updatedAt`;
- `archivedAt`.

Lifecycle:

1. Системные иконки доступны из начального каталога.
2. Пользователь выбирает иконку для категории.
3. Пользователь может добавить или настроить иконку, если MVP включает кастомизацию сверх выбора из каталога.
4. Иконка архивируется, если больше не должна выбираться для новых категорий; существующие категории сохраняют ссылку.

### ReportPeriod

Назначение: задает период аналитики, например месяц, квартал, год или произвольный интервал.

Владелец: текущий пользовательский запрос или сохраненная настройка пользователя, если продукт решит сохранять выбранные периоды.

Область видимости: только пользователь, который смотрит отчет.

Ключевые поля:

- `startDate`;
- `endDate`;
- `preset`, например month, quarter, year, custom;
- `timezone`.

Lifecycle:

1. Пользователь выбирает период.
2. Период применяется к аналитическому представлению.
3. Период может быть изменен без изменения финансовых данных.

### AnalyticsView

Назначение: вычисляемое представление для базовых отчетов по доходам, расходам, категориям и остаткам.

Владелец: текущий пользователь, который запрашивает аналитику.

Область видимости: формируется только из данных, доступных текущему пользователю, и дополнительно ограничивается выбранным `reportMode`.

Report modes:

- `shared family report`: включает только shared-счета, shared-операции и household-категории выбранного household.
- `combined viewer overview`: включает shared-счета household и personal-счета текущего `viewerUserId`; personal-счета, операции, категории и агрегаты второго участника не включаются.

Ключевые поля:

- `viewerUserId`;
- `householdId`, если открыт семейный контекст;
- `reportMode`: `shared_family_report` или `combined_viewer_overview`;
- `period`;
- `includedAccountIds`;
- `incomeTotal`;
- `expenseTotal`;
- `categoryBreakdown`;
- `accountBalances`;
- `generatedAt`.

Lifecycle:

1. Пользователь открывает отчет.
2. Система определяет видимые счета согласно `reportMode`.
3. Система фильтрует операции по периоду и видимости.
4. Система возвращает агрегаты без раскрытия личных счетов другого участника.

## Связи и cardinality

- `User 1 -> 0..many Membership`.
- `Household 1 -> 1..2 active Membership` в MVP.
- `Membership many -> 1 User`.
- `Membership many -> 1 Household`.
- `User 1 -> 0..many personal Account`.
- `Household 1 -> 0..many shared Account`.
- `Account 1 -> 0..many Operation`.
- `Operation many -> 1 Account`.
- `Operation 0..many -> 0..1 counterparty Account` для переводов.
- `Category 1 -> 0..many Operation`.
- `Icon 1 -> 0..many Category`.
- `User 1 -> 0..many personal Category`.
- `Household 1 -> 0..many household Category`.
- `ReportPeriod 1 -> 1 AnalyticsView` как параметр вычисления.
- `AnalyticsView many -> many Account` через набор видимых счетов.

## Ownership и visibility

| Объект | Владелец | Кто видит в MVP | Правило доступа |
| --- | --- | --- | --- |
| User | сам пользователь | сам пользователь; участникам семьи виден минимальный профиль | Полный профиль не раскрывается без необходимости |
| Household | создатель/семейное пространство | активные участники | Доступ через active Membership |
| Membership | Household | активные участники пространства | Управляет участием, не финансовыми правами |
| Personal Account | User | только владелец | Не раскрывается второму участнику семьи |
| Shared Account | Household | активные участники Household | Общий бюджет строится по этим счетам |
| Operation | Account | пользователи с доступом к счету | Видимость наследуется от счета |
| Personal Category | User | только владелец | Может применяться к личным операциям владельца |
| Household Category | Household | активные участники Household | Применяется к общим операциям |
| Icon | global/User/Household | по scope и владельцу | Не должен раскрывать приватные пользовательские данные |
| AnalyticsView | текущий пользователь | текущий пользователь | Агрегирует только видимые счета и операции |

## Инварианты

- Каждый `Account` имеет ровно один `ownershipType`: personal или shared.
- У personal-счета обязательно есть `ownerUserId` и нет обязательной зависимости от `householdId`.
- У shared-счета обязательно есть `householdId`; он виден только активным участникам этого household.
- Операция не может существовать без `accountId`.
- Операция income/expense должна иметь категорию видимого и подходящего типа.
- Операция должна иметь `createdByUserId`; при редактировании обновляется `lastEditedByUserId`.
- Пользователь может создавать и редактировать операции только на счетах, которые ему видимы.
- Для shared-счета операция должна использовать семейную категорию того же household или другую явно разрешенную для shared-контекста категорию.
- Для personal-счета операция не должна становиться видимой другим участникам семьи через аналитику, категорию, перевод или отчет.
- `shared family report` включает только shared-счета household и не включает personal-счета ни одного участника.
- `combined viewer overview` включает shared-счета household и personal-счета самого пользователя.
- Ни один report mode не включает personal-счета другого участника даже в агрегированном виде.
- Архивирование счета или категории не удаляет историю операций.
- MVP-операции имеют `sourceType = manual`; import/api-источники не требуются для создания валидной операции. Post-MVP safe auto-capture создает только pending draft и становится transaction только после user confirm/edit, поэтому итоговая операция остается manual-equivalent.
- Валюта операции должна быть совместима со счетом или явно обработана как обмен/перевод post-MVP; для MVP лучше не вводить сложную мультивалютную переоценку.

## Post-MVP вне текущей модели

Явно за пределами MVP:

- импорт Excel/CSV/файлов из банков, брокеров и других источников;
- распознавание источника, счета и типа отчета;
- экран проверки и корректировки импортированных операций;
- дедупликация импортированных операций;
- хранение импортных пакетов, файлов, банковских выписок и статусов обработки;
- полноценный SMS/push-import pipeline и прямые банковские API; реализованный post-MVP safe auto-capture ограничен Android opt-in pending drafts без server-side хранения raw SMS/notification body;
- массовая поддержка банков, брокеров и форматов отчетов;
- налоговая аналитика;
- инвестиционные рекомендации;
- продвинутая аналитика портфеля;
- детальные семейные роли и тонкая настройка приватности сверх правил personal/shared;
- выбор SaaS/self-hosted модели и связанные эксплуатационные решения.

Для будущего расширения в `Operation` допустимы поля `sourceType` и `externalReference`, но в MVP они не должны создавать зависимость от импорта или внешних источников. Capture draft хранит отдельный `idempotencyKey`/`evidenceHash` и статус `pending`/`confirmed`/`discarded`; дубликаты должны отсекаться до создания transaction.

## Открытые вопросы и риски

- Нужно решить, может ли пользователь создавать личные категории внутри семейного пространства или категории всегда выбираются из личного/семейного scope явно.
- Нужно уточнить, разрешены ли переводы между личным счетом одного участника и общим счетом семьи; безопасное MVP-правило: пользователь может переводить только между счетами, которые видит сам.
- Нужно определить минимальную модель валют: одна валюта на счет и операцию достаточно для MVP, но вклады и брокерские счета могут быстро потребовать расширения.
- Нужно уточнить, является ли `currentBalance` сохраняемым состоянием или всегда вычисляется из начального баланса и операций.
- Если второй участник покидает семейное пространство, нужно отдельно определить, сохраняет ли он доступ к историческим общим операциям за период участия.
- Кастомные иконки могут затронуть хранение файлов и модерацию контента; для MVP безопаснее начать с системного каталога и пользовательской настройки выбора.
- Брокерские операции в MVP должны оставаться учетными событиями без налоговой, портфельной и инвестиционной логики.
