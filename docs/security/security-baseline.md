# Security baseline MVP

## Контекст и границы

Этот baseline задает минимальный уровень безопасности для MVP приложения учета личных и семейных финансов.

MVP строится на следующих безопасных допущениях:

- банковские API, полноценный SMS/push-import pipeline и импорт файлов не входят в MVP; post-MVP safe auto-capture разрешен только как opt-in Android capture в pending drafts;
- счета и операции вводятся вручную;
- банковские токены, банковские пароли, SMS-коды, push-секреты и учетные данные брокеров не хранятся;
- raw body SMS/notification не отправляется на backend и не хранится server-side;
- личный счет видит только его владелец;
- общий счет видят активные участники семейного пространства;
- семейное пространство MVP рассчитано на двух участников без сложной ролевой модели.

Финансовые данные, даже введенные вручную, считаются конфиденциальными: названия счетов, остатки, операции, категории, отчеты и связи внутри семейного пространства могут раскрывать доход, долги, привычки, место работы, здоровье, отношения и инвестиционное поведение.

## Security goals для MVP

- Защитить личные финансовые данные пользователя от другого участника семьи, если данные относятся к личным счетам.
- Защитить общие семейные данные от пользователей вне семейного пространства.
- Исключить IDOR/BOLA: доступ к любому счету, операции, категории и отчету проверяется на сервере по владельцу или семейному пространству.
- Не хранить банковские секреты и не создавать скрытую зависимость от будущих интеграций.
- Обеспечить безопасную регистрацию, вход, выход, восстановление доступа и управление сессиями.
- Сделать действия с доступом, счетами, операциями и сессиями аудируемыми без записи чувствительных финансовых значений в логи.
- Обеспечить восстановимость данных через защищенные резервные копии и проверенный restore.
- Задать набор security acceptance checks для будущей QA-ветки.

## Минимальная threat/abuse model

### Активы

- Учетная запись пользователя: email/логин, парольный хеш, настройки безопасности.
- Сессии и refresh/access tokens.
- Личные счета, операции, категории и отчеты пользователя.
- Общие семейные счета, операции, категории и отчеты.
- Состав семейного пространства и приглашения.
- Резервные копии, журналы аудита, конфигурация и секреты приложения.

### Доверенные границы

- Клиенты Android и PWA считаются недоверенными: все проверки доступа выполняются на сервере.
- API считается единственной точкой доступа к данным приложения.
- База данных и хранилище backup доступны только backend-сервису и ограниченным эксплуатационным ролям.
- Логи и аналитика не являются местом хранения финансовых данных.

### Основные угрозы

- Credential stuffing, brute force, перебор email и учетных записей.
- Захват сессии через XSS, небезопасные cookies, утечку токенов или публичное устройство.
- IDOR/BOLA: доступ к чужому счету или операции через подмену `accountId`, `transactionId`, `familySpaceId`.
- Горизонтальное повышение привилегий между участниками разных семейных пространств.
- Утечка личных счетов через общие отчеты, поиск, категории, переводы, уведомления, audit/logs или ошибки API.
- Семейный insider abuse: участник семейного пространства пытается увидеть, изменить или вывести личные данные другого участника.
- CSRF для cookie-based PWA и небезопасный CORS.
- XSS через названия счетов, категории, описания операций и display name.
- SQL/NoSQL injection или unsafe query composition.
- Утечка данных через backup, дампы БД, debug logs, crash reports и frontend telemetry.
- Неправильная обработка приглашений: replay, перехват, принятие приглашения не тем пользователем.
- Потеря или порча данных из-за удаления, ошибки миграции или неработающего восстановления.

### Abuse-сценарии, которые MVP должен блокировать

- Пользователь A меняет URL/API id и получает личный счет пользователя B.
- Второй участник семьи видит личные счета первого участника в списке счетов, отчетах, поиске, категориях или переводах.
- Пользователь из другой семьи получает общий семейный счет через известный или угаданный id.
- Бывший участник семьи продолжает использовать старую сессию или старый invite token.
- Атакующий многократно пробует пароли или reset-токены без rate limit.
- Финансовые суммы, описания операций или названия счетов попадают в application logs, crash reports или frontend telemetry.
- Raw SMS/notification body, SMS-коды или notification secrets попадают в backend, logs, telemetry, audit, crash reports или backups.

### Safe auto-capture boundary

- Android capture включается только пользователем. SMS-capture использует `RECEIVE_SMS`, а не `READ_SMS`; notification capture требует включения Android notification listener в системных настройках.
- Backend принимает и хранит только structured capture draft, `idempotencyKey`/`evidenceHash`, confidence/metadata без raw body и статус `pending`/`confirmed`/`discarded`.
- `pending` draft не изменяет счета, остатки, отчеты и search/autocomplete. Transaction создается только после user confirm/edit и затем обрабатывается как manual transaction.
- `confirmed`/`discarded` lifecycle должен быть идемпотентным: повторное событие с тем же evidence не создает дубликат.
- Parser confidence ниже утвержденного порога обязан оставлять draft на ручную проверку или отклонять capture; автоподтверждение запрещено.

## Authn baseline

- Каждый пользователь имеет уникальный неизменяемый `user_id`; email/логин не используется как security boundary.
- Пароли хранятся только как стойкие хеши с солью: Argon2id предпочтительно, bcrypt допустим при корректных параметрах стоимости. Plaintext, reversible encryption и собственные алгоритмы запрещены.
- Минимальная политика пароля: не менее 12 символов, проверка против очевидно скомпрометированных/частых паролей, без искусственного требования сложных символов как единственной защиты.
- Регистрация и вход возвращают нейтральные ошибки, не раскрывающие наличие email.
- Для login, регистрации, восстановления пароля, resend email и приглашений обязательны rate limit и защита от перебора.
- Восстановление пароля использует одноразовый короткоживущий токен, хранит только хеш токена, инвалидирует старые reset-токены и завершает существующие сессии после смены пароля.
- Email verification рекомендуется до открытия семейного приглашения и восстановления пароля; если MVP запускается в закрытом пилоте без verification, это должно быть явно принято как риск.
- 2FA/passkeys не считаются обязательными для закрытого MVP с ручным вводом, но решение о 2FA должно быть эскалировано перед публичным запуском, SaaS-моделью или хранением более чувствительных секретов.

## Authz baseline

- Все API endpoints работают по принципу deny by default.
- Любой объект должен иметь явную область доступа: `owner_user_id` для личных данных или `family_space_id` для общих семейных данных.
- Проверки доступа выполняются на сервере для каждого запроса чтения, создания, изменения, удаления и построения отчетов.
- Клиентские фильтры, скрытые поля UI и неугадываемые UUID не считаются контролем доступа.
- Пользователь может читать и изменять только свои личные счета и операции.
- Активный участник семейного пространства может читать и изменять общие семейные счета и операции этого пространства.
- Пользователь вне семейного пространства не имеет доступа к общим счетам, операциям, категориям, отчетам и составу участников.
- Удаление финансовых объектов в MVP должно быть soft delete с audit event; физическое удаление допустимо только через отдельный maintenance-процесс с контролем backup/retention.
- Отчеты строятся только по объектам, к которым пользователь имеет доступ. Shared reports не должны подтягивать личные счета другого участника.
- Любые списки, автодополнения, search endpoints, aggregate endpoints и export/debug endpoints должны проходить те же authz-проверки, что и карточки объектов.
- Ошибки доступа должны быть безопасными: для объектов вне области доступа возвращать одинаково нейтральный ответ, не подтверждающий существование объекта.

## Минимальная модель доступа personal/shared account

### Сущности и области

- `User`: отдельная учетная запись.
- `FamilySpace`: семейное пространство MVP.
- `Membership`: связь пользователя и семейного пространства со статусом `active`, `invited`, `removed`.
- `Account`: счет с областью `personal` или `shared`.
- `Transaction`: операция, наследующая область доступа от счета или от явно связанной пары счетов.
- `Category`: категория должна быть либо пользовательской, либо семейной; смешивать области в одной записи нельзя.

### Personal account

- Владелец: один `owner_user_id`.
- Видимость: только владелец.
- Доступ второго участника семьи: запрещен по умолчанию, даже если оба пользователя находятся в одном `FamilySpace`.
- Операции по личному счету: видит и редактирует только владелец.
- Отчеты по личному счету: доступны только владельцу и не включаются в семейные агрегаты.
- Категории для личных операций: если категория пользовательская, ее название и иконка не видны второму участнику; если используется семейная категория, сама категория видна семье, но личная операция не видна.

Риски personal account:

- Утечка через семейные отчеты или общий баланс.
- Утечка через перевод между личным и общим счетом.
- Утечка через общие категории с чувствительным названием.
- Утечка через audit/logs, где actor/target могут раскрыть название или сумму.
- Ошибочное включение personal accounts в API list endpoints.

### Shared account

- Область: один `family_space_id`.
- Видимость: все активные участники этого семейного пространства.
- Доступ: активные участники могут читать shared account, добавлять и редактировать shared transactions, если продукт не введет более строгие роли.
- Приглашенный или удаленный участник не имеет доступа к shared data.
- Общие отчеты строятся только по shared accounts и shared transactions.
- Изменение состава семьи должно немедленно влиять на доступ к shared accounts и инвалидировать сессии/кэши удаленного участника.

Риски shared account:

- Участник семьи видит все shared transactions, включая описания, категории и историю изменений.
- Ошибочное размещение личной операции на shared account делает ее видимой семье.
- Удаленный участник может сохранить локальные копии уже просмотренных shared данных; MVP должен блокировать дальнейший доступ, но не может технически отозвать уже увиденное.
- Общие категории и названия счетов могут раскрывать личную информацию обоих участников.

### Переводы между personal и shared

- Перевод между личным и общим счетом является высоким privacy-risk.
- Безопасный MVP-вариант: хранить перевод как две связанные записи с разной областью видимости. Личная сторона видна только владельцу personal account; shared-сторона видна семье, но не раскрывает название, остаток и историю личного счета.
- Если техническая модель не поддерживает разные области видимости для сторон перевода, такие переводы нужно запретить в MVP или требовать явного подтвержденного product/security решения до реализации.
- Второй участник семьи не должен видеть personal counterparty, personal account id, personal account name, personal balance или личное описание операции.

## Требования к хранению финансовых данных

- База данных production должна использовать encryption at rest на уровне managed storage/volume/database.
- Передача данных между клиентом, API, базой, backup-хранилищем и внутренними сервисами выполняется только по защищенным каналам.
- Финансовые поля не логируются в plaintext: суммы, описания операций, названия счетов, остатки, категории с пользовательским названием, email и токены должны быть замаскированы или исключены.
- Пароли, reset-токены, invite-токены и session/refresh tokens не хранятся в plaintext.
- Банковские токены, банковские пароли, API-ключи банков/брокеров, SMS-коды и push-секреты не хранятся в MVP.
- Доступ backend-приложения к БД выдается через минимально необходимые права. Административные роли не используются приложением в runtime.
- Production dumps запрещено использовать в локальной разработке и QA без обезличивания и отдельного разрешения.
- Данные разных пользователей и семей должны иметь явные tenant boundaries на уровне схемы данных, индексов и запросов.
- Миграции БД должны проходить backup-before-change и rollback/restore план для изменений, затрагивающих финансовые данные.
- Field-level encryption для отдельных финансовых полей не является обязательным baseline для закрытого MVP, но становится предметом эскалации перед публичным запуском, SaaS-моделью, расширением состава команды эксплуатации или хранением банковских/API секретов.

## Аудит действий и событий безопасности

### Что аудировать

- Регистрация пользователя, подтверждение email, вход, выход, неуспешные попытки входа.
- Запрос и завершение восстановления пароля.
- Создание, принятие, истечение и отзыв приглашения в семейное пространство.
- Добавление, удаление и изменение статуса участника семьи.
- Создание, изменение, soft delete и восстановление счетов.
- Создание, изменение, soft delete и восстановление операций.
- Изменение области счета: personal/shared, если такая операция вообще разрешена.
- Изменение категорий, влияющих на отчеты.
- Отказы доступа к объектам вне разрешенной области.
- Изменение security-sensitive конфигурации и секретов.
- Backup, restore, failed restore и ручной доступ администратора к production данным.

### Как аудировать

- Audit event содержит: timestamp, actor_user_id, action, target_type, target_id, scope_type, scope_id, результат, request_id, IP/user-agent при наличии и без лишней детализации.
- Audit event не содержит суммы, остатки, описания операций, полные названия счетов, plaintext email в необезличенном виде, токены, пароли и секреты.
- Для финансовых изменений audit должен фиксировать факт изменения и идентификаторы, но не полные before/after значения чувствительных полей.
- Audit log должен быть append-only на уровне приложения; изменение или удаление audit entries допускается только через отдельную администраторскую процедуру с собственным аудитом.
- Retention audit logs для MVP: минимум 90 дней для закрытого пилота; перед публичным запуском срок должен быть согласован с юридическими и эксплуатационными требованиями.

## Управление сессиями

- Web/PWA с cookie-based auth: cookies только `HttpOnly`, `Secure`, `SameSite=Lax` или `Strict`; CSRF protection обязательна для state-changing запросов.
- Token-based auth для Android: access token короткоживущий; refresh token ротационный, отзывной и хранится только в защищенном хранилище платформы.
- Logout инвалидирует серверную сессию или refresh token.
- Смена пароля, подозрение на компрометацию, удаление участника семьи и отзыв доступа инвалидируют связанные сессии.
- Рекомендуемые лимиты MVP: idle timeout до 30 дней для доверенного устройства и shorter-lived access token; точные значения фиксируются при выборе auth-стека.
- Сессии должны иметь server-side revocation или эквивалентный механизм denylist/versioning.
- Session fixation предотвращается выпуском новой сессии после login и password reset.
- CORS должен быть allowlist-only для известных клиентов/доменов; wildcard с credentials запрещен.
- Frontend не хранит session/refresh tokens в LocalStorage, если есть безопасная альтернатива через secure cookies или platform secure storage.

## Секреты и конфигурация

- Секреты не хранятся в репозитории, markdown-документах, frontend bundle, mobile bundle, Docker image layers и логах.
- Production secrets передаются через secret manager или защищенные переменные окружения платформы с ограниченным доступом.
- Для dev, staging и production используются разные секреты, разные базы и разные внешние endpoints.
- Приложение должно fail closed при отсутствии обязательного секрета или использовании dev-secret в production.
- Секреты генерируются криптографически стойко и имеют план ротации.
- Доступ к production secrets выдается по least privilege и фиксируется в audit/операционном журнале.
- Любая утечка секрета требует немедленной ротации, ревокации связанных токенов и проверки логов/backup.
- Выбор обязательного хранилища секретов для production является escalation trigger, если до MVP уже выбран публичный SaaS или команда эксплуатации больше одного доверенного владельца.

## Резервное копирование и восстановление

- Production база и audit logs должны иметь автоматические encrypted backups.
- Backup-хранилище изолируется от runtime-учетной записи приложения; приложение не должно иметь права удалять backups.
- Минимальная цель MVP для закрытого пилота: ежедневный backup, RPO не более 24 часов, RTO не более 24 часов. Перед публичным запуском значения пересматриваются.
- Restore должен быть проверен до релиза MVP минимум один раз на отдельном окружении.
- Backup должен сохранять tenant boundaries; при выборочном восстановлении нельзя раскрывать данные другой семьи или пользователя.
- Доступ к backup и restore-процедурам аудируется.
- Перед рискованными миграциями финансовых таблиц обязателен свежий backup и проверенный rollback/restore plan.
- Backup не должен попадать в локальную разработку, публичные buckets, issue trackers, chat attachments или незащищенные файловые обменники.

## Защита от типовых угроз

- IDOR/BOLA: объектные authz-проверки на каждом endpoint, включая reports, search, autocomplete и bulk endpoints.
- Injection: только параметризованные запросы/ORM без ручной конкатенации пользовательского ввода.
- XSS: output encoding, sanitization для отображаемых пользовательских строк, CSP для PWA, запрет небезопасного HTML в названиях счетов/категорий/описаниях.
- CSRF: CSRF-токены или same-site стратегия для cookie auth; state-changing методы не принимают простые cross-site запросы.
- Brute force: rate limits, progressive delay, lockout/captcha после аномальных попыток без раскрытия существования аккаунта.
- Account enumeration: нейтральные ответы login/reset/register и одинаковая семантика ошибок доступа.
- Broken access control in reports: агрегаты, суммы и остатки фильтруются до агрегации, а не после.
- Insecure direct caching: private/no-store для чувствительных API responses, осторожная настройка CDN и browser cache.
- Sensitive logs: централизованная фильтрация логов, запрет debug-логов с request/response body в production.
- Dependency risk: dependency scanning перед релизом, обновление критичных CVE, запрет известных уязвимых auth/crypto библиотек.
- Transport security: HTTPS only для production/staging с реальными данными, HSTS перед публичным запуском.
- Mobile/PWA storage: финансовые данные в локальном кэше минимизируются; при необходимости кэш шифруется средствами платформы и очищается при logout.
- Error handling: stack traces, SQL errors и внутренние id окружения не возвращаются пользователю.

## Обязательно до релиза MVP

- Утверждена минимальная access model: personal account видит только владелец, shared account видят активные участники family space.
- Реализованы server-side authz checks для всех счетов, операций, категорий, отчетов, приглашений и членства.
- Покрыты тестами cross-user, cross-family и personal-vs-shared сценарии.
- Пароли хранятся через Argon2id или bcrypt с корректными параметрами; plaintext/reversible password storage отсутствует.
- Реализованы безопасные login/logout/password reset и rate limits.
- Сессии имеют secure storage, logout/revocation и защиту от CSRF/CORS ошибок.
- Audit events пишутся для auth, family membership, account/transaction changes и security-sensitive событий.
- Production/staging с реальными данными работает только через HTTPS.
- Секреты вынесены из репозитория и frontend/mobile bundles.
- База и backups имеют encryption at rest; restore проверен минимум один раз.
- Логи и telemetry проверены на отсутствие финансовых значений, паролей, токенов и invite/reset secrets.
- Явно подтверждено, что банковские токены, банковские пароли, SMS/push/API секреты, raw SMS/notification body и импорт файлов не входят в MVP и не хранятся server-side.
- Для переводов между personal и shared выбран безопасный вариант: split visibility или запрет до отдельного решения.

## Post-MVP

- 2FA/passkeys и управление доверенными устройствами.
- UI для просмотра и отзыва активных сессий.
- Более детальная семейная privacy/role model.
- Field-level encryption или application-level encryption для отдельных финансовых полей, если этого потребуют модель угроз, юрисдикция или SaaS.
- Формальная data retention и account deletion policy.
- Юридическая и комплаенс-проработка для публичного запуска и выбранных юрисдикций.
- Безопасный импорт Excel/CSV: file validation, malware scanning, sandboxed parsing, preview before commit, audit.
- Full SMS/push/API интеграции только после отдельной threat model для банковских и брокерских секретов. Post-MVP safe auto-capture уже ограничен opt-in Android draft-only режимом: `RECEIVE_SMS`, notification listener через системные настройки, no raw body server-side, user confirm/edit before transaction.
- Хранилище банковских/API токенов с envelope encryption/HSM/KMS и отдельной процедурой ротации.
- Security monitoring, alerting, SIEM/use cases для подозрительных authz отказов, brute force и массового доступа.
- Периодический pentest или focused security review перед публичным релизом.

## Escalation triggers

Эскалировать к Security Architect/Product/Legal/Operations до реализации или релиза, если появляется любое из условий:

- Нужно принять обязательное решение по юрисдикции, комплаенсу, публичному запуску или обработке персональных данных.
- Нужно выбрать SaaS, self-hosted или hybrid deployment как product/business commitment.
- Нужно сделать 2FA/passkeys обязательными или отказаться от них перед публичным запуском.
- Требуется field-level encryption, client-side encryption или отдельное шифрование финансовых полей.
- Нужно выбрать production secret manager, KMS/HSM или схему хранения master keys.
- Появляются банковские API, брокерские API, банковские токены, банковские пароли, SMS/push секреты, raw SMS/notification body server-side storage или импорт файлов.
- Требуется расширить семейную модель за пределы двух участников или добавить детальные роли и приватность.
- Возникает необходимость показывать личные счета одному участнику семьи по решению другого участника.
- Нужно разрешить переводы между personal и shared без split visibility.
- Restore не проходит, backup оказывается неполным, или есть риск потери финансовых данных.
- Обнаружена критичная authz-ошибка, утечка финансовых данных, утечка секрета или повторная неудача security acceptance checks.

## Security acceptance checks для будущей QA-ветки

- Пользователь не может получить личный счет другого пользователя по прямому API id.
- Участник семьи не видит личные счета второго участника в списке счетов.
- Участник семьи не видит операции личного счета второго участника через прямой API id.
- Общий семейный счет виден обоим активным участникам семейного пространства.
- Пользователь из другого семейного пространства не видит shared account, shared transactions и shared reports чужой семьи.
- Shared reports не включают personal accounts второго участника.
- Personal reports владельца включают только его доступные personal accounts и допустимые shared accounts.
- Search/autocomplete не возвращают названия личных счетов другого участника.
- Category endpoints не раскрывают пользовательские private categories другого участника.
- Перевод personal -> shared не раскрывает семье personal account name, personal account id, personal balance и личное описание.
- Удаленный участник семьи теряет доступ к shared accounts и shared reports без повторного входа.
- Старый invite token нельзя использовать повторно после принятия, истечения или отзыва.
- Password reset token одноразовый, короткоживущий и не работает после смены пароля.
- Logout инвалидирует текущую сессию или refresh token.
- После смены пароля старые refresh tokens больше не работают.
- Cookie-based PWA запросы защищены от CSRF для state-changing действий.
- CORS не допускает wildcard origin с credentials.
- Login и password reset не раскрывают наличие email.
- Rate limit срабатывает на многократные login/reset/invite попытки.
- XSS payload в названии счета, категории и описании операции не исполняется при отображении.
- SQL/NoSQL injection payload в фильтрах отчетов не меняет область доступа и не ломает запрос.
- Production-like logs не содержат суммы, описания операций, названия счетов, пароли, reset tokens, invite tokens и session/refresh tokens.
- Audit event создается для login, failed login, password reset, invite accepted/revoked, account create/update/delete, transaction create/update/delete и access denied.
- Backup создается encrypted и restore успешно проходит на отдельном окружении.
- В репозитории и клиентских bundles отсутствуют production secrets.
- В MVP отсутствуют поля, endpoints или настройки для хранения банковских токенов, банковских паролей, SMS/push секретов, raw SMS/notification body и банковских API credentials; safe capture хранит только structured draft, `idempotencyKey`/`evidenceHash` и status lifecycle.
