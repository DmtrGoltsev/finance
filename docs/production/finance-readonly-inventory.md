# Диагностика схемы production Finance

Workflow `.github/workflows/finance-prod-readonly-inventory.yml` не развёртывает
сервисы и не меняет хост. Прямой SSH/SCP с рабочей станции запрещён. После
слияния изменений в `main` владелец вручную запускает `workflow_dispatch` **на
`main`** с `phase=bootstrap` и подтверждением `finance-readonly-inventory`.
До слияния обновлённый workflow недоступен для ручного запуска.

## Две фазы

1. `bootstrap` проверяет владельца, `main`, точное подтверждение и отсутствие
   внешнего `bootstrap_run_id`. Только этот job получает `contents: write` и
   `actions: write`. Он создаёт `prod/release-inventory-<run-id>` из точного
   SHA `main` через GitHub API, используя **только** `GITHUB_TOKEN` запуска.
   Ветка не создаётся с рабочей станции и не получает новых коммитов.
2. Тем же `GITHUB_TOKEN` bootstrap вызывает `workflow_dispatch` с
   `phase=inventory` на созданном ref. GitHub не запускает push-workflow от
   событий, созданных `GITHUB_TOKEN`, но делает исключение для
   `workflow_dispatch`. См. [правило GitHub](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow).
   Production deploy workflow отдельно отвергает `prod/release-inventory-*`
   до подготовки релиза и обращения к окружению, даже при ручном запуске.
   Ответ [API версии 2026-03-10](https://docs.github.com/en/rest/actions/workflows?apiVersion=2026-03-10#create-a-workflow-dispatch-event)
   должен содержать точный `workflow_run_id`: поиск по ветке/SHA запрещён.
   Пустой ответ не даёт выбрать run и останавливает bootstrap. По точному ID
   bootstrap ограниченно ждёт временно неполные метаданные. Несовпадение
   заголовка `display_title` при ещё работающем дочернем запуске также
   считается временным: GitHub может опубликовать окончательный заголовок
   позже. Если он не совпал к завершению запуска, это отказ. Противоречие
   ID, actor, ref, SHA, workflow ID, события или номера попытки отклоняется
   сразу; bootstrap остаётся активным до завершения дочернего run.
   После подтверждённого завершения он удаляет только собственный ref с
   прежним SHA, даже при неуспешной инвентаризации. Если дочерний run не
   завершился к пределу ожидания, ref сохраняется для проверяемой очистки.
3. Отдельный `validate-inventory` без production secrets проверяет строгий
   формат ref, SHA, actor `github-actions[bot]` текущего запуска, первую
   попытку, точные ID, имя и фазу обоих запусков, а также происхождение
   активного owner-started bootstrap-run на `main`. Чужой ручной dispatch не
   проходит. Только после его успеха job `inventory` получает существующие SSH
   secrets окружения `production`. Политика `prod/release-*` пропускает этот
   временный ref; `deployment: false` не создаёт запись о развёртывании.
4. Inventory обращается к хосту только из Actions с закреплённым host key и
   `StrictHostKeyChecking=yes`. Скрипт читает метаданные и фиксированные
   loopback health endpoints; не выводит значения `.env`, полный Docker
   inspect, DSN, секреты или содержимое финансовых данных. Только имена
   переменных читаются из `/etc/finance/backend.env`. При доступном backend
   Python ограниченный запрос читает номер Alembic, наличие таблицы outbox,
   размер текущей БД и `max_connections` внутри транзакции `READ ONLY`;
   ошибки скрываются и дают `unknown`. Проверка
   `validate_output.py` требует полный список полей, типизированные значения,
   отсутствие повторов и неизвестных полей **до** показа или загрузки вывода.
5. Bootstrap ждёт завершения inventory. Затем он удаляет только собственный
   ref, повторно проверив, что его SHA всё ещё равен исходному SHA `main`.
   Если запуск не найден, ожидание истекло или SHA изменился, автоматическое
   удаление не выполняется.

## Если временный ref остался

Не отправлять в него коммиты и не запускать deploy workflow. Записать ID и SHA
bootstrap-run, по ним найти inventory-run и дождаться завершения всех его
jobs. Сверить, что ref имеет точное имя
`prod/release-inventory-<bootstrap-run-id>` и всё ещё указывает на исходный
SHA `main`. Только после этих трёх проверок владелец может удалить именно этот
ref через GitHub API. При изменившемся SHA или активном run остановиться и
разобрать ситуацию; не применять массовую очистку `prod/release-*`.

## Границы доказательства

Артефакт версии `finance_inventory_v5` содержит только фиксированные флаги,
состояния служб, коды HTTP без тел ответов, ограниченные имена учётных записей
и групп, метаданные ОС, объём памяти и свободного места, путь службы Finance
из узкого списка, ограниченный путь рабочего каталога, версию `pg_dump`,
номер Alembic и SHA-256 имени хоста. Последний позволяет сопоставить хост с
ранее подтверждённым именем, не публикуя его в артефакте. Пустые `User` и
`Group` у загруженной службы обозначаются `default`; это не доказательство
фактического UID/GID запущенного процесса.

Версия v5 также фиксирует наличие и версии Node/npm, наличие версий Node 22/24
в **локальном индексе** `apt-cache` без обновления индекса, размеры/свободные
байты и inode для `/opt` и `/var/lib/postgresql`, тип и ограниченное имя точки
монтирования по `findmnt`, память и swap, размеры разрешённых каталогов и
RSS/CPU основных PID трёх служб. Числа отражают момент запуска, а `%CPU` от
`ps` не является прогнозом пиковой нагрузки. Размер `postgres_wal_bytes`
является частью `postgres_data_bytes`, их нельзя складывать. Поле
`finance_prior_releases_bytes` есть разность размера всего каталога releases
и текущего выпуска: учитывает служебные блоки каталога, а общие inode/жёсткие
ссылки могут ограничивать точность этой оценки. Путь PostgreSQL измеряется
только в пределах `/var/lib/postgresql`; если данные или WAL перенесены, размер
будет неполным либо `unknown`. Артефакт не раскрывает имена выпусков, файлов,
процессов, устройств, содержимое каталогов и ответы SQL кроме чисел.

`apt_cached_node22_available=no` означает лишь отсутствие Node 22 в текущем
локальном индексе; это не проверка доступности внешних репозиториев. Размер БД
не равен размеру `pg_dump`, а свободное место не заменяет проверку на пик
установки, сборки, резервного копирования и миграций. Для backup runbook
отдельно требует не менее 1 ГиБ свободного места в файловой системе каталога
резервных копий. Диагностика не создаёт backup и не проверяет его пригодность.

`n8n_loopback_health` по прежнему контракту проверяет порт `5680`, а новое
`n8n_5678_http_status` проверяет `/healthz` на документированном для
N8NAgents порту `5678`. Значение HTTP `000` означает, что код ответа не
получен. Ненулевой код сам по себе не доказывает, что ответил именно n8n.
Сопоставление имени хоста и `/opt/n8n-stack/current` требуется отдельно.
Для портов `5680` и `8000` выводится только класс слушателя: нет,
только loopback или есть не-loopback. Это не проверка доступности извне.

`sudo_n_list_available` и `sudo_n_docker_listed` проверяют только правила
`sudo -n -l`; команды с повышенными правами не исполняются. Даже `yes` не
разрешает применять `sudo` для управления Docker. `*_writable=yes` означает
права SSH-пользователя на существующий каталог, а не разрешение устанавливать
там сервис. Отсутствие Docker CLI или доступа к daemon не доказывает
отсутствия Docker на хосте. Сетевую достижимость из контейнера в host backend
этот read-only скрипт не проверяет.

Признаки `DEEPSEEK`, `FCM` и `DELIVERY`+`HMAC` означают только присутствие
подходящего **имени** в `/etc/finance/backend.env`, но не значение, пригодность
учётных данных или наличие настроек в других файлах. Общая готовность
provider credentials остаётся `unknown`. Если backend venv, файл окружения
или безопасное соединение с БД недоступны, `alembic_current` и
`outbox_table_present` равны `unknown`; скрипт не выполняет миграций.
Имена environment secrets GitHub можно проверить отдельно через
`gh secret list --env production`; значения не извлекать.

Если GitHub ограничивает `GITHUB_TOKEN` в создании веток или dispatch,
bootstrap завершится с ошибкой. Не использовать PAT, GitHub App token,
локальный push в `prod/release-*` или изменение branch policy как обход.
GitHub документирует действие `GITHUB_TOKEN` от имени Actions, но не обещает
в справке конкретное значение actor для дочернего `workflow_dispatch`.
Поэтому проверка `github-actions[bot]` намеренно закрыта при несовпадении.
В предыдущем запуске actor был `github-actions[bot]`, а ранний заголовок API
временно отличался от окончательного. При будущем несовпадении actor
остановиться и выбрать другой диагностический маршрут; менять branch policy
или ослаблять проверку неизменяемых полей нельзя.
