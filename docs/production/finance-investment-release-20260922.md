# Подготовка выпуска инвестиционных рекомендаций Finance

Состояние: локальная подготовка, без отправки ветки и развёртывания. Ветка
`prod/release-finance-investment-recommendations-20260922` объединяет
`a3d3368c726d7908066943072ae719035a7508c6` с тремя коммитами
`origin/main` о ротации пароля через обычное слияние. Продукционный выпуск
пока заблокирован: отправка этой ветки запускает CI, но общий шлюз выпуска
останавливается до обращения к хосту. Не удалять эту защиту только ради
успешного запуска workflow.

## Подтверждённый контур

- Существующий backend работает как `finance-backend.service` и слушает
  `127.0.0.1:8081`; PWA обслуживается из `/var/www/finance/current`.
- Новый worker и n8n/gateway описаны двумя Compose-файлами, которым нужна
  внешняя сеть `finance_backend_internal`. Gateway отправляет callback на
  фиксированный `finance-backend:8000`, а worker обращается к `n8n:5678`.
  Связь этих адресов с действующей неконтейнерной установкой не определена.
- Три workflow находятся в `ops/finance-n8n/workflows`. Импорт оставляет их
  неактивными. Для HTTP-узлов требуется Header Auth credential с идентификатором
  `finance-gateway-token`; способ его безопасного создания/сопоставления на
  действующем экземпляре не утверждён.
- В окружении GitHub `production` по именам обнаружены старые SSH-секреты
  `HEXCORE_PROD_SSH_*`, но нет переменных или секретов для новых сервисов.
  Значения секретов не считывались.

## Данные, необходимые для завершения pipeline

1. Утверждённая топология на HexCore: есть ли Docker/Compose, точные пути
   установки и внешних env/secret-файлов, владелец каталогов, способ связать
   host backend с закрытой сетью без публикации внутренних webhook; проверяемые
   адреса в обоих направлениях. Нужен выбор между адаптацией контейнерного
   контракта и отдельной host-службой worker. Не подставлять адреса наугад.
2. Подтверждение существования и прав сети `finance_backend_internal`, а также
   способ подготовки PostgreSQL gateway на уже существующем томе с резервной
   копией. Compose init-скрипт срабатывает только на новом томе.
3. Внешнее защищённое хранение и способ внедрения значений, перечисленных в
   `ops/finance-n8n/.env.example` и `ops/finance-delivery/.env.example`:
   отдельные DB credentials, `N8N_ENCRYPTION_KEY`,
   `FINANCE_GATEWAY_QUEUE_KEY`, `FINANCE_GATEWAY_TOKEN`,
   `FINANCE_INGRESS_HMAC_SECRET`, `FINANCE_CALLBACK_HMAC_SECRET`,
   `DEEPSEEK_API_KEY`, `FINANCE_BACKEND_DATABASE_URL`, а при включённом push
   `FINANCE_BACKEND_FCM_PROJECT_ID` и внешний service-account файл.
   Согласовать соответствия ingress/callback ключей с `/etc/finance/backend.env`.
   Не передавать значения через workflow inputs, Git или журналы.
4. Порядок установки образов, резервных копий обеих новых БД и ключей,
   восстановления, проверки health, безопасного импорта и активации ровно трёх
   workflow, а также отката worker/n8n/gateway без отката финансовой БД.
   Уточнить, кто подтверждает реальный Docker smoke, DeepSeek, MOEX и FCM.
5. Свежая ревизия Alembic на production, состояние backup/restore и окно
   обновления. Репозиторий нацелен на единственную голову `20260921_0025`;
   текущее состояние хоста не опрашивалось. Особая проверка нужна для
   совместимой уже существующей `outbox_events` перед ревизией `0021`.

## Порядок после закрытия блокеров

1. Зафиксировать install-контракт, добавить в workflow поэтапные preflight,
   сборку/передачу всех компонентов, установку PostgreSQL/gateway/n8n,
   безопасный credential/import/activation, worker и health. Общее production
   условие должно остаться закрытым до доказательства полного набора.
2. Прогнать CI-only `workflow_dispatch` на точном SHA без обращения к хосту.
   Затем проверить host preflight, резервные копии, Alembic lineage и сценарий
   отката штатными GitHub Actions с закреплённым SSH host key.
3. После утверждения всех ворот снять временную блокировку отдельным
   проверенным коммитом. Только затем отправлять release-ветку: push по
   действующему регламенту сам разрешает production deploy.
4. Сохранить URL запуска, SHA, release ID, контрольные суммы, ревизии БД,
   результаты health и проверок worker/n8n/gateway, а также обезличенное
   свидетельство восстановления. Прямые SSH/SCP и ручное развёртывание
   запрещены.
