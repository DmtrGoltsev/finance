# Эксплуатация Finance n8n и шлюза

## Запуск и проверки

Порядок: PostgreSQL → шлюз → n8n → назначение Header Auth credential → импорт/активация проверенных workflow → подписанный `scripts/health.ps1` → worker Finance. Проверить отсутствие опубликованных портов PostgreSQL/gateway и внешний `404` для внутренних webhook.

Мониторинг: готовность трёх контейнеров, возраст `queued`, просроченный захват, число `delivery_failed`, свободное место и наличие актуальных резервных копий. Содержимое очереди, HMAC-заголовки, ответы модели и пароли не журналировать. Доступ к редактору n8n только через loopback/SSH-туннель.

Перед production обязательно выполнить `npm run smoke` с доступным Docker. Он создаёт собственные тома, проект и изолированную backend-сеть, без обращения к настоящему backend или DeepSeek. Проверить отдельно полный Finance → n8n → gateway → Finance с тестовым аккаунтом; этот smoke его не заменяет.

## Копирование и восстановление

`scripts/backup.ps1 -Destination <каталог> -EnvFile .env` создаёт custom dump БД n8n и БД gateway, копии workflow/кода/схем и SHA-256. Бинарные dump передаются через `docker cp`, не текстовый конвейер PowerShell.

Копии содержат зашифрованные credentials n8n и временные финансовые пакеты gateway. Они конфиденциальны даже в зашифрованном виде. Перенести их в защищённое удалённое неизменяемое хранилище. `.env`, `N8N_ENCRYPTION_KEY` и `FINANCE_GATEWAY_QUEUE_KEY` хранить отдельно; без ключей восстановленные задания не расшифровать. Автоматизация удалённых копий данной веткой не создаётся.

`scripts/restore-drill.ps1 -BackupDirectory <копия> -EnvFile .env -Confirmation RESTORE_TO_ISOLATED_DATABASE` проверяет хеши, восстанавливает обе копии в новые временные БД, проверяет основные таблицы и удаляет только эти временные БД. Во всех командах используется пользователь из `POSTGRES_USER`, а не имя `finance_n8n`. Production-БД не переключается. Дополнительно перед выпуском проверить расшифровку синтетического задания восстановленным ключом.

## Откат

Остановить n8n и gateway, не удаляя БД и очередь. Зафиксировать безопасные счётчики. Вернуть совместимые версии образа шлюза и workflow из одной резервной копии. `scripts/rollback.ps1` требует обе версии образов и явное подтверждение. Запустить шлюз и n8n, выполнить health, импортировать workflow без активации, проверить повтор события и совместимость очереди. Только затем включать обработку. Не возвращать старые Code-node workflow поверх новой очереди.

## Ошибки

При отсутствии свежего времени MOEX анализ завершается ошибкой, даже если HTTP успешен. На выходных данные могут намеренно не пройти лимит 24 часа. Не подменять дату текущей и не запрашивать котировки у модели.

После сбоя callback проверить фактическое состояние задания в Finance. `delivery_failed` сохраняет зашифрованный исходный результат до 30 дней. Повтор исходного события возобновляет только сохранённый callback, но не генерацию. После удаления результата по сроку хранения шлюз возвращает `DELIVERY_RESULT_EXPIRED`; ключ защиты от дублей сохраняется бессрочно. Не очищать запись ради повторной генерации, не ставить `ready` вручную, не записывать напрямую в БД Finance.

Для задания Finance с `failed` и `lastErrorCode=delivery_failed` владелец использует «Повторить доставку» в Android или `POST /api/v1/investments/recommendation-jobs/{jobId}/retry-delivery` с действующей авторизацией. Сохраняются исходные job/event/idempotency key. Смотрите `ops/finance-delivery/README.md`. Автоматическое восстановление иных ошибок callback этим маршрутом не выполняется.

После восстановления старой копии pending-заданий сначала сверить их с Finance: копия БД не доказывает, что callback не был принят после момента копирования. Не активировать очередь вслепую.
